# Compatibility

Three kinds of evidence back this page.

- **Conformance** runs the same test cases against the vendor's own package and against this repository's entry point. `@neondatabase/serverless` 1.2.0 runs against a stand-in for Neon's `/sql` endpoint and, for `Pool` and `Client`, against the PostgreSQL wire protocol over a WebSocket to PGlite. `@planetscale/database` 2.0.0 and 1.20.2 run against a stand-in for PlanetScale's HTTP API over SQLite. Our entry points run against the `pgsql` and `mysql` RPC contract simulators. A case which passes for both shows that the two packages return the same thing. The suites are in `packages/*/test/conformance`.
- **Simulator** means the real adapter code runs against a contract simulator in `test-support/`: PGlite (a real PostgreSQL) for `@surrealdb/pg` and SQLite for `@surrealdb/mysql`, both behind the `pgsql` and `mysql` RPC shapes of the engine's client contract. It verifies call forms, result shapes, `instanceof` checks, type parsers and transaction handling. It does not verify engine behaviour: SQL dialect coverage, value encodings, SQLSTATE mapping or OIDs.
- **Server** means the integration suite against a built `surreal` binary: the engine's main branch built with `storage-mem,http,scripting,postgres,mysql`. The `pgsql` and `mysql` methods and the drop-in behaviours listed below are merged there.

## Conformance matrix

Status values:

- **supported**: the conformance case passes for the vendor and for this package.
- **differently**: the case passes with a documented difference.
- **impossible**: SurrealDB or the RPC contract cannot carry it; the reason is given.
- **missing and doable**: none remain. The rows marked "added" were found missing by the suites and implemented in the change that introduced them.

#### Field metadata

The contract's `columns` carry `name`, `type` (the protocol type code), `nullable`, `table` and `column`. They do not carry the column length, the collation or the flag bits. This package derives them from the type, as the MySQL protocol reports them for a column of that type without a declaration: the default display width (`INT32` is 11, `INT64` is 20, `VARCHAR` is 1020), `charset` 63 for binary and numeric types and 255 (utf8mb4) for text, and `flags` with `NOT_NULL` (1) when `nullable` is `false`, `NUM` (32768) for numbers, and `BLOB` (16) and `BINARY` (128) for blobs.

To report the real values, the engine would add `length` (the declared character or byte length, or the display width), `charset` (the collation id), `flags` (or `unsigned`, `primary_key`, `auto_increment` and `zerofill` as booleans) and `decimals` to the `mysql` column objects of the `columns` array of a statement result. Until then `unsigned` integers report as signed, and `columnLength` is the type's default.

## Engine behaviours

Against the first engine to serve the methods, six behaviours blocked or worked around parts of the adapters. They are fixed in the engine's main branch (the `pgsql` and `mysql` methods, then the drop-in compatibility change), and the client carries no workaround for any of them:

1. `RETURNING` answers its columns in the order the statement names them, so Drizzle and Prisma read the rows correctly.
2. `valueMode: "text"` gives plain decimal text, with no `30i32` suffix.
3. `BEGIN ISOLATION LEVEL ...`, `START TRANSACTION READ ONLY`, `WITH CONSISTENT SNAPSHOT` and `SET TRANSACTION` open or configure a real transaction. The node-postgres and mysql2 layers send the text as written. `READ UNCOMMITTED`, `READ COMMITTED` and `REPEATABLE READ` run as `snapshot`, which the SQL standard allows.
4. Text parameters are read as the type of the column they are written to, compared with an integer key, written to a link column, or used as `LIMIT` and `OFFSET`. This needs the column to be declared (`DEFINE FIELD ... TYPE`), and does not apply in a request that also holds DDL.
5. Errors carry the SQLSTATE and MySQL error number a client branches on (`42P01`, `23505`, `23502`, `22P02`, `40001`, `1146`, `1062` and so on).
6. Atomic calls take `isolation` and `readOnly`, and an uncommitted atomic call marks the entries that ran as `rolled_back` (`rolledBack` on a result).

JSON cannot carry an integer beyond 2^53 exactly. The node-postgres layer reads in text mode, so an `int8` is exact; the native API with the JSON transport is not. The conformance fakes cannot exercise that range either: `node:sqlite` refuses to read such an integer, so the PlanetScale cases use a 64-bit value inside the safe range.

Where the Neon and PlanetScale options cannot be carried by the engine contract, the entry points refuse or ignore them as the matrix above says. The `neon()` function and the PlanetScale client assume the engine answers the `pgsql` and `mysql` calls with `valueMode: "text"` and per-entry `vars` in atomic calls; the integration suites run exactly that against the server.

## Running

```bash
bun install
bun run build              # also needed for the built-output tests
bun run test               # unit
bun run test:conformance   # the vendor packages against the same cases as this repository's
bun run test:compat        # generates the Prisma client, then runs the adapter suites
SURREAL_BIN=/path/to/surreal bun run test:integration
```
